# 对比实验：Agent 用 AgentCAD vs Agent 直接写代码

日期：2026-10-27。问题：同样的绘图任务，让 Codex 通过 AgentCAD 操作，和让 Codex 直接写 Python（ezdxf）代码，效果差多少？

**结论先说**：在这 6 个简单任务上，**两种方式画出的图同样正确**，差别不在正确性。直接写代码用的输入 token 少约 45%，但耗时多一倍；版面各有好坏；AgentCAD 的产出在 AutoCAD 审核中全部 0 错误，直接写代码有 1 张出错。这组任务太简单，没能体现 AgentCAD 的主要价值（事务、回滚、改图安全、AutoCAD 互通），下一步需要更难、更接近真实工作的任务。

## 怎么比的

| | A 组：AgentCAD | B 组：直接写代码 |
|---|---|---|
| Agent | Codex CLI 0.163，推理强度 high | 同左 |
| 能用什么 | 只有 AgentCAD 的 MCP 工具，沙箱只读，不能运行命令 | 可以写文件、运行命令；Python 环境里只有 ezdxf 1.4.5，工作目录在仓库外，接触不到 AgentCAD |
| 任务 | T1 法兰、T2 长圆孔板、T3 阶梯轴、T4 A3 图框、T5 建筑平面、T6 修改别人的法兰图 | 同左，任务文字完全相同，只有开头说明不同 |
| 自我检查 | 要求调用 `validate_drawing` | 要求用代码重新读取 DXF 核对 |

两组同时运行（各 3 个并行）。评分不用 AgentCAD 自己的验证器，而用一个只依赖 ezdxf 的中立评分脚本（[grade.py](../examples/trials/grade.py)），按"关键点是否落在实际几何上"检查几何，并区分真正的尺寸标注实体和用线条加文字假装的标注。评分维度参考了 [AutoCAD-Bench](https://benchlm.ai/benchmarks/autocadbench)（几何、尺寸、注释、版面）和 [ComCADBench](https://arxiv.org/pdf/2606.13239)（DXF 几何检查、必需的标注）。另外每张图都用 AutoCAD 2027 审核并打印成 PNG，由我逐张目视检查。

每个任务每组只跑了 1 次，样本小，单个任务的差异可能是偶然的。

## 结果

### 正确性（中立评分）

| 任务 | A 几何 | B 几何 | A 尺寸标注 | B 尺寸标注 |
|---|---|---|---|---|
| T1 法兰 | 5/5 | 5/5 | 3 个标注 + 1 个引线注释（6×Ø12） | 4/4 |
| T2 长圆孔板 | 5/5 | 5/5 | 7/7 | 7/7 |
| T3 阶梯轴 | 6/6，台阶和倒角轮廓线**有** | 6/6，台阶和倒角轮廓线**没有** | 6/6 | 6/6 |
| T4 A3 图框 | 2/2，文字 13/13 | 2/2，文字 13/13 | — | — |
| T5 建筑平面 | 6/6 | 6/6 | 4/4 | 4/4 |
| T6 改图 | 4/4，无残留旧标注 | 4/4，无残留旧标注 | 4/4 | 4/4 |

两组都没有画错任何几何，都用了真正的尺寸标注实体，单位都正确。阶梯轴的轮廓线差异不能归因于哪种方式：A 组在上一轮也漏画过。

### AutoCAD 审核与目视

| 任务 | AutoCAD 审核 A / B | 目视（AutoCAD 出图） |
|---|---|---|
| T1 法兰 | 0 / 0 | **B 更好**：水平引线标注放在零件外，清楚；A 的标注文字倾斜，Ø60 和 Ø110 的尺寸线穿过中心互相交叉 |
| T2 长圆孔板 | 0 / 0 | **A 更好**：B 的 "R8" 文字飘在图纸左上角、离圆角很远，"Ø20" 文字也和尺寸线脱开 |
| T3 阶梯轴 | 0 / 0 | **A 更好**：有台阶和倒角轮廓线，箭头符合机械制图；B 漏轮廓线，并且用了建筑制图的斜线端点 |
| T4 A3 图框 | 0 / **2** | **B 更好**：B 自己画了中文标题栏（名称、图号、材料、比例），字大清楚；A 用的是内置标题栏，字段名是很小的英文。B 的 2 个审核错误是脚本遍历整个文档时把图纸空间视口移到了非 0 图层 |
| T5 建筑平面 | 0 / 0 | 基本相同，都自行设置了出图比例；A 的墙线有线宽，略好 |
| T6 改图 | 0 / 0 | 都正确 |

### 成本

| | A：AgentCAD | B：直接写代码 |
|---|---|---|
| 交互次数 | 每个任务 8–14 次工具调用 | 每个任务 4–11 条命令 |
| 输入 token（6 个任务合计） | 281 万（缓存命中约 89%） | 154 万（缓存命中约 92%） |
| 输出 token（合计） | 2.1 万 | 3.3 万 |
| 耗时 | 平均 122 秒（78–155） | 平均 263 秒（179–431） |
| 中途出错 | 3 个任务撞到 `modify` 不支持尺寸标注，改用删除重建 | 无工具错误；Agent 自己读回检查时发现并修正了问题（重复 Ø、标注比例放大 100 倍） |
| 自报是否属实 | 6/6 属实 | 6/6 属实（都承认没有做 CAD 目视检查） |

A 组输入 token 多，主要因为操作目录和每次调用返回的结构化结果都进入上下文。B 组耗时长，主要因为写脚本、运行、读回核对需要更多模型输出。

## 怎么看这个结果

1. **简单任务上，直接写代码已经足够好。** ezdxf 本身很成熟，模型也熟悉它，6 个任务的几何和标注全对，还会自己读回检查。"Agent 写代码"这条路不能被忽视，前面提到的"让代码生成计划、由 Runtime 执行"（`run_script`）方向值得做：它能拿到代码方式的 token 优势和表达能力。
2. **这组任务没有测到 AgentCAD 的主要价值。** 原子事务、检查点回滚、操作日志、改图时只动该动的实体、AutoCAD 互通（DWG）、出图可读性检查，在这些一次成型的小任务里都用不上。B 组唯一的审核错误（误改视口图层），正是"代码能碰到整个文档"带来的副作用，但只出现了一次，不能据此下结论。
3. **AgentCAD 暴露出的短板要补。** `modify` 不支持尺寸标注（6 个任务里 3 个撞到）；内置标题栏是英文小字，不适合中文图纸；默认的直径标注样式不如引线标注清楚。
4. **版面质量两边都不稳定**，而且两种自我检查都发现不了，只有出图目视能看到。这一点和上一轮实测的结论一致。

## 下一步建议

- **做难一点、贴近真实工作的任务**，才能分出高下：例如对一张已有的复杂图纸连续做 5 轮修订（中间要求撤回一次）、在真实 DWG 上改图并导回 DWG、按国标出一张带多个视图的零件图、批量生成 20 张参数不同的图。
- **每组至少跑 3 次**，看稳定性而不是单次结果。
- **补上 AgentCAD 的短板**：`modify` 支持尺寸标注、中文标题栏、更清楚的默认标注样式。
- **试做 `run_script`**，再加入第三组对比。
